## 何を測りたかったか

太陽熱養生の効果は「地温が上がる」と説明されます。ただ、**何度まで、どの深さまで、何時間**上がるのかを書いた資料が見つかりませんでした。土の消毒は温度と時間の積で効くので、この3つが分からないと「やってよかった」以上のことが言えません。

なので、測る道具から作りました。

要件はこうなりました。

- **深さ方向に複数点**。表面だけ熱くても意味がない。15cm・25cm・40cm。
- **区画ごとに独立**。比較試験をするので、3区画に同じ構成を3セット。
- **畑に置きっぱなしで2か月**。電源もネットもない場所で動き続けること。
- **データが消えないこと**。通信が切れても後から回収できること。

## 構成

```
[測定ユニット × 3台]
  ├── DS18B20 × 7本（防水型）
  ├── SDカード（ローカル記録）
  └── Raspberry Pi Pico W
       │  MQTT over WiFi
       ↓
  [モバイルルーター（SORACOM SIM）]
       ↓
  [サーバー] ── SQLite に記録
       ↓
  グラフ表示
```

| 部材 | 仕様 | 数量 |
|---|---|---|
| マイコン | Raspberry Pi Pico W（RP2040 + CYW43439） | 3 |
| 温度センサー | DS18B20 防水型 | 21（7本 × 3台） |
| 基板 | 自作・JLCPCB 発注 | 3 |
| SDカード | ローカル二重記録用 | 3 |
| 防水ボックス | 屋外設置用 | 3 |
| 通信 | カシムラ KD-249 + SORACOM plan-K2 | 1 |

センサーは1台あたり7本。畑の**中央**と**端部**にそれぞれ 15cm・25cm・40cm の3本ずつ、残り1本を外気温に割り当てました。端部を測るのは、被覆の縁から熱が逃げる量を見るためです。

### 1-Wire をやめて個別GPIOにした

DS18B20 は1本のバスに複数ぶら下げられるのが売りで、最初はその設計にしていました。やめました。

バス方式だとセンサーのIDを読んでから「このIDが中央15cm」という対応表を作る必要があります。畑で1本挿し替えるたびに対応表を更新することになり、間違えたときに気づけません。**GP8〜GP14 に1本ずつ割り当てる**方式に変えて、GPIOピン番号がそのまま埋設位置を意味するようにしました。配線は7倍になりましたが、現場での取り違えがなくなりました。

## 作って分かったこと

### 基板のフットプリントを2か所間違えた

実装して初めて気づいたものが2つあります。

**電源入力の端子台**は、データシート上は2穴のフットプリントで合っているはずが、実物は 3.5×5mm 配置の4本足（電気2本＋固定爪2本）でした。固定爪をニッパーで落として実装しています。

**スライドスイッチ**はもっと厄介で、使ったフットプリント側は COM が外側パッドに割り当てられているのに、部品（SS-12SDP2）は COM が物理的に中央ピンでした。中央ピンがトレースのない穴に刺さって電気的に浮きます。中央ピンとポリヒューズ側の外ピンをはんだでブリッジして回避しました。

どちらも「データシートの寸法図は見たが、ピンの割り当てまで実物と突き合わせていなかった」のが原因です。

### 送信間隔が30分から21秒に崩れた

計測を始めてしばらくして、**データは届き続けているのに送信間隔だけが壊れている**という症状が出ました。設定は30分のはずが、実測21秒間隔。

ウォッチドッグが発火して再起動を繰り返していました。原因を MQTT だと思って長く探したのですが、違いました。**MQTT の送信はその手前で完了していて、詰まっていたのはその後のクラウドサービスへの HTTP POST** です。タイムアウトもウォッチドッグの餌やりも入れていない場所で、現場の細い回線が詰まると8秒で落ちる。データが届き続けるのは、落ちる前に MQTT が終わっているからでした。

手元のシミュレータで再現したら実測19.0秒。現場の21秒とほぼ一致したので確定しました。

ついでに分かったことが2つあります。

- **RP2040 のウォッチドッグ上限は約8.4秒**。`WDT(timeout=60000)` は起動時に例外で落ちます。つまり現場で完全に沈黙する。「タイムアウトを1分に伸ばす」はウォッチドッグでは実現できないので、ソフト側のリトライ予算として実装し直しました。
- **`connect()` の後にソケットのタイムアウトを設定しても無意味**。ライブラリは `connect()` の中で応答待ちをするので、一番詰まりやすい場所を通り過ぎた後になります。ソケット生成時からタイムアウトを乗せる方式に変えました。

### SDカードが3台とも読めなかった

ローカル二重記録用の SD カードは、3台すべてでマウントに失敗しました。レギュレータのはんだ不良か、カードソケットの接触不良と見ています。結果として記録はサーバー側の1系統だけになりました。

幸い通信は安定していて実害は出ませんでしたが、「二重化したつもりが一重だった」という状態で2か月走らせたことになります。**冗長化は、冗長側が動いていることを確認して初めて冗長化**です。

## ラベルと実際の深さがずれた

これは機器というより運用の失敗です。

設置時に、データベース上のラベル（`S1_center_10cm` など）と実際の埋設深さがずれました。**ラベルは10cm、実際は15cm**です。

気づいた時点でラベルを直すべきでしたが、直しませんでした。ファームウェアの書き換えは畑でしかできず、書き換えるまでは新旧のラベルが混在してグラフの系列が割れるためです。結果として、**表示する側で読み替える**という扱いが2か月続きました。

このサイトのデータでは `label_actual` という列を追加して解決してあります。元のラベルは残したまま、実際の位置を別の列で持たせる形です。

もうひとつ、区A・区Bの7本目のセンサーは途中（7/28 8:50）で**外気温から土壌5cmに差し替え**ています。同じラベルのまま意味が変わっているので、この系列は参考値として扱い、積算温度の計算には入れていません。

## 現場で失ったもの

2か月の計測で失われたデータをまとめておきます。

| 内容 | 影響 |
|---|---|
| 区Cの受信率が76%（区A 92% / 区B 99%） | 区Cの積算温度は絶対値の信頼度が低い |
| 区C 端部40cm のプローブが最終日に断線 | 校正値が取れず、この1本だけ補正できない |
| SDカードのローカル記録が全台失敗 | 二重化が機能せず |
| 読み取り失敗による 0.0℃ が53件 | 集計から除外（区A・端部15cm、全約130万件中） |

区Cだけ受信率が低いのは、モバイルルーターから一番遠い区画だったためと考えています。

---

## サーバー側

データはクラウド上の MQTT ブローカーで受けて、SQLite に保存していました。手元の Raspberry Pi でも同じブローカーを購読して二重に保存し、Grafana で見る構成です。

**計測終了にともない、クラウド側は2026年9月に停止しました。** このサイトのグラフは書き出し済みの静的データを読んでいるので、サーバーが止まっても表示は変わりません。確定データは CSV と JSON で手元とリポジトリに残してあります。
